# The Refuge — Full Handoff Document

Everything you need to understand, maintain, and extend the system.
Written for someone who vibe-codes with limited git knowledge and
collaborates with Claude to build things.

---

## What it is

The Refuge is your private online library for completed roleplay chats.
It runs entirely on GitHub Pages (free, static hosting) as a set of
client-side HTML/JS pages — nothing server-side, no databases, no
hosting costs. Stories are encrypted before they leave your machine;
the repo stores gibberish files that only your passphrase can unlock.

The system has two jobs:

1. **Get a chat from raw export to sealed story** (the Pipeline)
2. **Read, browse, and manage your sealed library** (the Reading Room)

## Typography

- **Display font:** Fraunces (variable, optical sizing) — used for
  the wordmark, story titles, and the page heading.
- **Body font:** Spectral — used for all prose, summaries, card text.
- **Mono font:** IBM Plex Mono — used for labels, eyebrows, tags,
  buttons, and the story index.
- All loaded from Google Fonts. Offline fallback: Georgia / system mono.

### Reader

- Prose renders at `--prose-size` (default `1.12rem`) with `line-height: 1.78`.
- The **Aa** button cycles four size+width modes:
  `1.02rem / 42rem`, `1.12rem / 52rem`, `1.24rem / 62rem`, `1.38rem / 72rem`.
- Headings in the prose are flattened to body size and weight (semibold,
  same font) — quiet section markers, not billboards.
- Reading position is saved per story per device in `localStorage`
  (key: `rr_pos_` + filename).

## Encryption

All three sealing/reading pages use identical crypto:

- **Algorithm:** AES-256-GCM
- **Key derivation:** PBKDF2 with SHA-256, **310,000 iterations**
- **Salt:** 16 random bytes per file
- **IV:** 12 random bytes per file
- **Package format:** `{v:1, salt: base64, iv: base64, ct: base64}`

The passphrase is **never stored on GitHub** and is **not recoverable**.
If you lose it, the sealed files are unreadable. Your Google Drive
originals in `AI/The Refuge` are the safety net.

The "Remember on this device" checkbox stores the passphrase in
`localStorage` (key: `rr_pass`). The **Lock** button clears it.

### Filename generation

Each sealed file is named `story-XXXXXX.json` where `XXXXXX` is the
first 3 bytes (6 hex chars) of a SHA-256 hash of:

```
scenario + "|" + part + "|" + title + "|" + date
```

This means: same story name + same part + same chapter title + same
date = same filename (idempotent re-sealing overwrites cleanly).
Different chapters get different filenames automatically.

## The data model (inside each sealed file)

When decrypted, a story is a JSON object:

```json
{
  "title": "The Meeting",        // Chapter title (optional)
  "part": "1",                   // Part number (optional)
  "character": "Gale",           // Character name
  "scenario": "The Tell",        // Story name (groups chapters)
  "tags": ["slow-burn", "amnesia"],
  "status": "complete",
  "date": "2026-07-05",
  "summary": "A mentalist meets a woman who cannot be read.",
  "body": "The full story text in markdown..."
}
```

### How fields map to the UI

| Field | Shelf card | Reader header | Filter rail |
|-------|-----------|---------------|-------------|
| `character` | Eyebrow (left) | Eyebrow (left) | Character filter |
| `date` | Eyebrow (right, "Jul 2026") | Eyebrow (right) | — |
| `scenario` | **Card title** (large) | **Page title** (large) | Story filter |
| `part` | Chapter line ("PART 1") | Chapter line | Sort order within story |
| `title` | Chapter line ("· The Meeting") | Chapter line | — |
| `summary` | Card body (italic) | Subtitle (italic) | — |
| `tags` | Chips at bottom (sorted, max 3) | — | Tags filter |
| `status` | — | — | Status filter |
| `_file` | — | — | Story index |

### Vocabulary mapping (old → new)

If you encounter old field names in earlier conversations or files:

| Old name | New name | Notes |
|----------|----------|-------|
| Scenario | Story Name | Groups chapters together |
| Title | Chapter Title | Optional, defaults to Story Name if blank |
| — | Part Number | New field, orders chapters within a story |

## Tags

### Central tag list: `tags.txt`

One tag per line, lowercase, in the repo root. This is the canonical
list. Two ways to manage it:

1. **Edit directly on GitHub:** go to the repo, click `tags.txt`,
   pencil icon, add your tags, commit.
2. **From the Pipeline:** Archive stage → Manage your tag list →
   type a new tag → "Add & save to repo" (pushes via GitHub API).

### How tags flow

```
tags.txt (repo) ──fetch──> localStorage cache ──> autocomplete dropdown
                                                       │
                    GitHub API <──push── "Add & save"   │
                                                       ▼
                                              tag chips on story
                                                       │
                                              sealed inside .json
                                                       │
                                              library reads from .json
                                                       ▼
                                              filter rail on shelf
```

### Tag autocomplete

Click the Tags field and a dropdown shows all known tags. Type to
narrow. Pick to add. Tags always forced to lowercase. If you type
something new, the last dropdown option offers "+ add new tag".
Chosen tags appear as oxblood chips above the field; click × to remove.

### GitHub token (for "Add & save to repo")

One-time setup. Generate at:
**github.com → Settings → Developer settings → Personal access tokens
→ Fine-grained tokens**

- Repository access: **the-reading-room only**
- Permission: **Contents: Read and write**
- Paste in the Pipeline's tag manager panel; stored in `localStorage`
  only (key: `rr_gh_token`), never sent anywhere except GitHub directly.

## The manifest robot

`.github/workflows/build.yml` runs automatically whenever a file
changes in `stories/`. It lists every `.json` file in `stories/` and
writes the list to `manifest.json`. The library reads this file to
know which stories to decrypt.

- Uses `actions/checkout@v4.2.2` (Node.js 24 compatible)
- Requires **Settings → Actions → General → Workflow permissions →
  Read and write** (set once)
- Commits as `reading-room-bot`

You never edit `manifest.json` by hand.

## Everyday workflows

### Adding a new story (full pipeline)

1. **Export** the chat from Claude / CrushOn; save raw copy in
   Drive → `AI/The Refuge`.
2. Open **Pipeline** (`pipeline.html`).
3. **Extract:** drop the exported file. The format is detected
   automatically (`.mhtml`, `.json`, `.md`, `.txt`, `.zip`).
4. **Check:** review turns, toggle include/exclude, pick the
   start and end of the actual story.
5. **Archive:** fill in Story Name, Part, Chapter Title, pick
   Tags from the autocomplete, write a one-line Summary, enter
   your passphrase. Click **Seal & download**. Optionally click
   **Text copy** or **Markdown copy** for an unencrypted backup.
6. Save the `story-XXXX.json` to:
   `C:\Users\cathe\GitHub Repositories\the-reading-room\stories`
7. GitHub Desktop: short summary → **Commit to main** → **Push origin**.
8. Live in about a minute.

### Adding a new story (quick prepare)

For already-clean text that doesn't need Extract/Check:

1. Open `tools/prepare.html` (at its https:// address).
2. Paste text, fill in fields, pick tags, enter passphrase.
3. **Seal & download** → save to `stories/` → commit → push.

### Editing an existing story

1. Open **Edit sealed** (`pipeline.html#edit`).
2. Drop the `.json` file, enter passphrase, click **Unseal**.
3. Edit metadata (Story Name, Part, Chapter, Tags) and/or the
   story text directly.
4. Click **Re-seal & download**. Optionally grab a **Markdown copy**
   or **Text copy** as a backup.
5. Replace the old file in `stories/` with the new one
   (same filename if title/part/date unchanged).
6. Commit → push.

### Removing a story

Delete the `.json` from `stories/`, commit, push. The robot rebuilds
the manifest automatically.

### Reading

- Enter your passphrase at the gate (or let "Remember" skip it).
- Browse the shelf, filter by Character / Story / Tags / Status,
  or search.
- Click a card to open the reader.
- **Aa** cycles text size and width.
- **Theme** cycles light / dark / night.
- **‹ Prev** / **Next ›** navigate between chapters of the same story.
- **Export .md** downloads the decrypted story as a markdown file.
- **Pipeline** and **Edit sealed** links in the reader bar let you
  navigate out without re-locking.
- Scroll position is remembered per story.

### Managing tags

- **Quick way:** edit `tags.txt` on github.com (pencil icon, add
  lines, commit).
- **From the Pipeline:** Archive → Manage your tag list → type a
  new tag → "Add & save to repo".
- Tags inside already-sealed stories can only be fixed by
  re-sealing those stories.

## What each page does NOT do (known limits)

- **The Library** does not sync tags from `tags.txt` — it reads tags
  from inside the sealed stories only. The tag filter shows exactly
  what's sealed. Tag consistency depends on sealing correctly.
- **Prepare** cannot push new tags to the repo — it's read-only for
  tags. Use the Pipeline's Archive stage or edit `tags.txt` directly.
- **The converter** (`mhtml-converter.html`) is not themed (legacy
  purple gradient). It has a Refuge nav bar for navigation but is
  otherwise untouched. Superseded by Pipeline's Extract.
- **Edit sealed** does not have its own tag manager panel — it uses
  the same tag library as Archive. Manage tags from Archive's panel.
- **The reader** does not support in-browser editing of the prose.
  To edit, use Edit sealed in the Pipeline.

## Markdown rendering (in the Library reader)

The reader converts stored markdown to HTML line-by-line:

- `# Heading` and `## Heading` → `<h2>` (flattened to body size/weight)
- `### Heading` and deeper → `<h3>` (same flattening)
- `**bold**` → `<strong>`
- `*italic*` → `<em>`
- `_italic_` → `<em>` (only when not inside a word like `file_name`)
- `> blockquote` → `<blockquote>`
- `---`, `***`, `§` → `<hr>` (rendered as § section marker)
- Blank lines separate paragraphs
- Headings only consume their own line (no heading-swallow bug)

## Security model (honest assessment)

**What's protected:**
- Story content: encrypted with AES-256-GCM, unreadable without passphrase
- Metadata (title, tags, summary): encrypted inside the same package
- Filenames: neutral hashes (`story-431027.json`), reveal nothing

**What's visible to anyone with the URL:**
- The site exists (the HTML, CSS, JS are public)
- How many stories you have (number of files in `stories/`)
- The file sizes (rough indication of story length)
- `tags.txt` (your tag vocabulary — consider whether this reveals anything)
- `landing.html`, `pipeline.html` (the tools themselves, not the content)

**What's NOT protected:**
- `tags.txt` is in the clear — if your tags alone reveal something
  sensitive, consider moving them into the encrypted model in future
- The GitHub token in `localStorage` — anyone with access to your
  browser's dev tools on that machine can read it. Fine-grained
  scope (one repo, contents only) limits the blast radius.

**The passphrase:**
- Not recoverable. Not stored on GitHub. Only in your browser if
  "Remember" is ticked.
- Your Google Drive originals (`AI/The Refuge`) are the safety net.
- If you change your passphrase, all previously sealed stories
  become unreadable — you'd need to re-seal every one with the new
  phrase.

## How to hand this to a future Claude session

If you need to continue building on this system with Claude (or
Claude Code), share this document plus these files:

1. `index.html` — the library (552 lines)
2. `pipeline.html` — the pipeline (1,475 lines)
3. `tools/prepare.html` — the prepare tool (273 lines)
4. `landing.html` — the home page (150 lines)
5. `tags.txt` — the tag list
6. `.github/workflows/build.yml` — the manifest robot

Key things the next session needs to know:

- Crypto parameters must match across all three sealing/reading
  files (310,000 iterations, AES-GCM, PBKDF2-SHA256)
- Internal field name is `scenario` even though the UI says
  "Story Name" — never rename the internal field or old stories break
- `actions/checkout@v4.2.2` not bare `@v4` (Node.js 20 deprecated)
- The tag library syncs from `tags.txt` via fetch on page load;
  writes back via GitHub API (needs the token)
- The markdown renderer is line-by-line, not block-based — this was
  a bug fix; don't revert to block splitting
- Story sort: within a story name, sort by part number ascending;
  across stories, sort by newest date first
